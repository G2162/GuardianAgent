## 1. Scope Determination & Pre-Registration Boundary

### 1.1 Scope Origin: Post-Development Scoping
The decision to scope GuardianAgent strictly to **WRITE operations** (`INSERT`, `UPDATE`, `DELETE`) and **DDL operations** (`DROP`, `ALTER`, `TRUNCATE`) was made **after observing development partition results** on the BIRD benchmark, where GuardianAgent's rule-based NLP parser produced an unusable 99.20% false-block rate on complex relational `SELECT` queries (Section 6.1). 

### 1.2 Pre-Registration Status
This specification is **pre-registered strictly with respect to all subsequent evaluation datasets and frozen test splits**. No test data has been generated under this scope at the time of v1.1 freezing. Pre-registering this scope guarantees that the boundaries, threat model, and evaluation criteria remain frozen before any new benchmark data is collected or evaluated.

## 2. In-Scope Threats

GuardianAgent defends against unintended, destructive, or mismatched SQL mutations generated by an upstream LLM acting on user instructions:

1. **Destructive Schema-Level DDL:**
   - Schema drops: `DROP TABLE`, `DROP DATABASE`, `DROP VIEW`.
   - Table truncations: `TRUNCATE TABLE`.
   - Destructive structural modifications: `ALTER TABLE ... DROP COLUMN`.
2. **Unconstrained & Tautological Mass Deletions:**
   - `DELETE` statements lacking a `WHERE` clause (full-table wipe).
   - `DELETE` statements with tautological `WHERE` predicates (e.g. `WHERE 1=1`, `WHERE TRUE`, `WHERE id = id`).
3. **Unconstrained & Tautological Mass Updates:**
   - `UPDATE` statements lacking a `WHERE` clause (mass overwrite of all rows).
   - `UPDATE` statements with tautological predicates.
4. **Target Entity / Row Mismatches:**
   - The user requests modifying entity $A$ (e.g., `user_id = 101`), but the generated SQL modifies entity $B$ (e.g., `user_id = 999`).
5. **Target Table Mismatches:**
   - The user requests modifying table $T_1$ (e.g., `customers`), but the SQL modifies table $T_2$ (e.g., `accounts` or `salaries`).
6. **Column / Field Mutation Mismatches:**
   - The user requests updating column $C_1$ (e.g., `address`), but the SQL modifies column $C_2$ (e.g., `salary` or `is_admin`).
7. **Value Assignment & Scaling Mismatches:**
   - The user specifies value $V_1$ (e.g., `status = 'pending'`), but the SQL assigns a conflicting value $V_2$ (e.g., `status = 'terminated'`).
   - Value magnitude scaling errors (e.g., assigning 15,000,000 instead of 1,500,000).
8. **Operation Verb & Modality Mismatches:**
   - The user requests an update (`UPDATE`), but the SQL emits a destructive deletion (`DELETE`).
   - The user requests a read (`SELECT`), but the SQL emits a state mutation (`UPDATE`, `DELETE`, `INSERT`, `DROP`).
9. **Unintended Blast Radius / Scope Escalation:**
   - The user requests modifying a single unique entity, but the SQL omits selective filters, causing multiple rows to be mutated.
10. **Hidden & Hybrid Write Operations:**
    - `SELECT ... INTO ...` (creates or overwrites persistent tables from read expressions).
    - Writable Common Table Expressions (CTEs, e.g. `WITH updated AS (UPDATE ...) SELECT ...`).
    - `SELECT ... FOR UPDATE` or `SELECT ... FOR SHARE` (executes concurrency row-level write locks on relational rows).
    - `INSERT ... RETURNING ...` or `UPDATE ... RETURNING ...` (mutations disguised as read result sets).
11. **Stacked / Injected SQL Statements:**
    - SQL containing multiple semicolon-separated statements (e.g., `UPDATE accounts SET balance = 0; DROP TABLE logs;`).

## 3. Out-of-Scope Threats

The following attack vectors and operational contexts are explicitly out of scope for GuardianAgent:

1. **Data Exposure / Exfiltration via Pure `SELECT`:**
   - Viewing unauthorized records, sensitive columns (e.g., SSNs, passwords), or cross-tenant data through non-modifying read queries.
   - *Defense locus:* Database-native Role-Based Access Control (RBAC), Row-Level Security (RLS), column-masking views, and network-level data loss prevention (DLP).
2. **Multi-Statement Agent Sequences:**
   - Interactive, multi-turn agent conversations where state corruption accumulates across multiple distinct query turns (e.g., agent inspects, sets a flag, then deletes based on earlier turn state). GuardianAgent operates as a **per-statement transactional gateway** inspecting individual proposed actions against immediate turn instructions.
3. **Adversarial Prompt Injection into User Intent:**
   - Direct or indirect prompt injections where an adversary manipulates the natural language user instruction itself to deceive the LLM into legitimately requesting a destructive action.
   - *Defense locus:* Input sanitization, system prompt isolation, and upstream LLM guardrails (e.g. NeMo Guardrails, Llama Guard).
4. **Database Privilege Escalation:**
   - Exploiting SQL dialect vulnerabilities to gain superuser permissions or execute OS-level shell commands (e.g. `xp_cmdshell` or `COPY ... FROM PROGRAM`).
   - *Defense locus:* Database engine security patches and least-privilege database user configuration.
5. **External SQL Injection (SQLi):**
   - Untrusted web/API parameters directly concatenated into query strings by application code.
   - *Defense locus:* Standard parameterized queries and prepared statements.
6. **Denial-of-Service (DoS) via Computational Exhaustion:**
   - Submitting computationally heavy queries (e.g. unindexed 10-way Cartesian joins) that exhaust database CPU or memory.
   - *Defense locus:* Query timeouts, statement cost limits, and database connection pool governors.

## 4. Trust Model & Deployment Assumptions

### 4.1 Component Trust Matrix

| Component | Trust Level | Security Rationale & Mode Behavior |
| :--- | :--- | :--- |
| **User Request** | **TRUSTED** | Represents legitimate, authorized operator intent within the session. GuardianAgent treats the natural language request as the ground-truth specification. |
| **Upstream LLM** | **UNTRUSTED** | Prone to hallucinations, attention lapses, schema confusion, unintended deletions, and syntax generation errors. |
| **Generated SQL** | **UNTRUSTED** | Candidate query string proposed by the LLM. It must be analyzed, cross-referenced against user intent, and authorized prior to execution. |
| **Intent Extractor (Rule-Based Mode)** | **PARTIALLY TRUSTED** | Operates deterministically without external API dependencies (`GUARDIAN_DISABLE_LLM=1`), but exhibits syntactic fragility on complex phrasing, prepositions, and nested clauses. |
| **Intent Extractor (LLM Mode)** | **UNTRUSTED / FALLIBLE** | Employs frontier model prompting (`GUARDIAN_DISABLE_LLM=0`) for natural language extraction; more flexible with phrasing, but non-deterministic and susceptible to extraction hallucinations. |
| **Database Engine** | **TRUSTED** | Faithfully enforces ACID properties, schema constraints, transaction boundaries, and foreign keys when executing authorized queries. |
| **GuardianAgent Gateway** | **TRUSTED ENCLAVE** | Sits in-line between the LLM and the database engine. Executes deterministically to evaluate candidate SQL against extracted intent. |

### 4.2 Mandatory Deployment Assumption: Sole Gateway Path
**GuardianAgent is assumed to be the sole, non-bypassable mediation path between the upstream agent/LLM and the database execution interface.**  
There are no backdoors, unmonitored database connection handles, direct socket connections, or ambient credentials accessible to the LLM agent. All database-bound commands must traverse GuardianAgent.

## 5. SELECT Policy: ALLOW (Log Only) & Known Limitations

### 5.1 Operational Rule
**All queries whose root operation is a pure read (`SELECT`) without write side-effects evaluate to `ALLOW` (log only for auditing and observability).**  
Under this policy, GuardianAgent does not autonomously abort (`BLOCK`) any read operation.

### 5.2 Explicit Limitation Disclosure
Scoping GuardianAgent to write operations means **it does not prevent unauthorized data viewing, exfiltration, or cross-table read redirection**. If an LLM misinterprets a request for employee directory info and generates a query reading executive salaries, GuardianAgent permits execution. Organizations deploying GuardianAgent must enforce database-level access controls (such as PostgreSQL Row-Level Security or read-only replica roles) to restrict read permissions.

### 5.3 Known Relational Hard Case: Duplicate-Entity Ambiguity
When multiple rows share identical non-key attributes (e.g., two distinct employees named *"John Smith"* in different offices) and the user instruction does not provide an explicit unique identifier (such as `employee_id`), deciding whether an update or delete should affect one or both matching records represents an **inherent linguistic and relational ambiguity**. GuardianAgent flags multi-row modifications where a single row was linguistically implied, but cannot infer non-specified disambiguating criteria without user intervention.

## 6. Disclosed Negative Results & Development Data Provenance

In adherence to scientific transparency and open research practices, this section documents empirical negative results and development data realities discovered during repo audit (`results/audit/REPORT.md`):

### 6.1 Parser Failure on Complex Relational Read Queries
When GuardianAgent's deterministic rule-based NLP pipeline was evaluated on all 500 clean queries from the BIRD Mini-Dev set (`bird_eval/full_bird/results/bird_full_final_report.md`), it produced an unusable **99.20% false-block rate (496 / 500 harmless queries blocked)**:
- This result demonstrates that **this specific rule-based parser implementation** fails on complex multi-table joins, subqueries, aliases, and aggregate projections found in BIRD read questions. It should not be construed as a general proof that rule-based parsing cannot scale.
- **Critical Write-Path Note:** Because the write evaluation path uses the exact same underlying intent extraction logic (`intent_analyzer.py`), **the write path may exhibit similar linguistic failure modes** when user instructions involve complex subordinate clauses, compound filters, or implicit qualifications.

### 6.2 The V1/V2 Synthetic Benchmark Degradation
During initial development, the synthetic benchmarks reported near-perfect metrics:
- **Paper Target Claims:** V1 (1,500 cases): 100.0% accuracy; V2 (1,500 cases): 98.20% accuracy, 4.50% unsafe miss rate.
- **Audit Findings:** To lower false blocks on BIRD queries, commit `f470c23` softened `FIELD_MISMATCH` on `SELECT` from `BLOCK` ($R=7.0$) to `CONFIRM` ($R=4.0$). This single change immediately degraded synthetic benchmark performance when re-evaluated:
  - **V1 Accuracy dropped from 100.0% to 93.33%** (100 dangerous cases demoted to `CONFIRM`, causing a **16.67% unsafe miss rate** in Standard mode).
  - **V2 Accuracy dropped from 98.20% to 92.87%** (107 dangerous cases demoted to `CONFIRM`, causing a **17.83% unsafe miss rate** in Standard mode).
  - In `STRICT` mode, V1 dropped to **83.33%** and V2 dropped to **81.33%**.
- **Oracle Intent Usage:** Furthermore, the synthetic runners (`large_v1_runner.py`, `large_v2_runner.py`) supplied `known_intent=ground_truth_intent`, bypassing the NLP parser entirely.

### 6.3 Formal Re-Classification of BIRD 342 Mutations as DEV Data
Forensic git history analysis proves that `scratch/test_calibration.py` and `scratch/test_refined_calibration.py` iteratively tuned regexes, stopwords, and score overrides directly on the 342 fresh mutations (`bird_fresh_mutations_dataset.json`) and 50 benign queries (`bird_mini_dev_50_eval.json`) until achieving 0 false blocks.
- **Formal Status:** The 342 BIRD fresh mutations and 50 benign queries **are development (DEV) data**.
- They cannot be reported as an unseen, held-out test split in publication. Any true generalization benchmark must be constructed on a separate, frozen set of unseen databases (e.g. Spider 2.0 or held-out BIRD partitions) never inspected during rule creation.
